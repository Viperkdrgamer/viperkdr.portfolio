CodeVisualizer

Live 3D/2D codebase graph for Roblox Studio — scan scripts, stream to a local backend, render as an interactive force graph.

This one started as a fun idea more than a utility — I wanted to visualize how code flows through a project and make it look as cool as it felt to build. It's more web-integrated than plugin-first, streaming your entire script tree to a browser and rendering it as a live 3D force graph. Not everything needs a serious reason behind it. Sometimes the best projects are the ones you build just to see if you can. The video shows an early version — the graph rendering and node system have come a long way since.

CodeVisualizer — Full system pipeline
  • Batched HTTP over one large payload — large codebases can have hundreds of scripts. Sending 20 per request with a 1s delay keeps Studio responsive and avoids HttpService timeouts on large projects.
  • Version polling instead of WebSockets — the browser polls /version every 5 seconds and only fetches the full graph when the version number changes. This keeps the frontend stable during a scan without needing a persistent connection.
  • Source stored separately from the graph — the graph data endpoint strips source code for a fast initial render. Source is only fetched when a user clicks a node, keeping the graph payload small.
  • Recursive ancestor resolution in the backend — the plugin sends flat script paths like ServerScriptService.Systems.Combat.Handler. The backend walks the path and creates folder nodes as needed, so the plugin never needs to know about the graph structure.

UI Manager Plugin

Declarative UI state management for Roblox Studio — no manual scripting required.

This wasn't built for coders — it was built for builders and UI designers who have zero scripting experience and don't want to learn. That's a valid position to be in, and they shouldn't have to write a script just to make a button open a menu. This plugin gives them a way to manage UI states visually, without touching code at all.

UI Manager — Event Flow
  • Centralized controller over per-element scripts — eliminates duplicated logic and makes UI state predictable. Any element can be controlled from one place.
  • Event-driven dispatch — the controller doesn't call UI methods directly; it fires events that UI elements subscribe to, keeping coupling low.
  • Plugin-native widget — runs inside Studio, not in-game, so developers get real-time feedback during building without deploying to a live server.

Card Game + Web API

Cross-platform card game with a live web dashboard — Roblox and browser in sync via a shared API.

A trading card game built in Roblox with a companion website. Players authenticate via API key to view their card collection in a browser — the same data that drives the in-game experience, synced through DataStore and a REST-style web layer.

Card Game — Cross-platform data flow
  • API key auth instead of OAuth — simpler to implement within Roblox's HttpService constraints while still keeping player data private. Each player gets a unique key stored in their DataStore entry.
  • DataStore as the single source of truth — both the game and the web layer read from the same data, avoiding sync conflicts. The web layer is read-only to prevent tampering.
  • JSON serialization at the bridge layer — Roblox tables are converted to JSON before leaving the platform, keeping the web backend platform-agnostic.

Database Editor Pro

A visual DataStore editor for Roblox Studio — inspect, edit, and manage live game data without code.

Most DataStore editors were paid, and I genuinely dislike that. Dev tools should be free — knowledge and workflow shouldn't sit behind a paywall. So I built a full rival that's completely free and open source, with guides showing exactly how to use it in-game. It supports every data type you'd need: byte data, buffer data, custom types — all without writing a single line of code. You can switch between Roblox DataStore and your own external database, set custom themes, and the UI is built to be as approachable as possible. It also has an audit log tracking who changed what and when, plus per-collaborator permission control — you can decide exactly what someone else in your Studio session is allowed to do: add, modify, delete. The video is an older version; a lot of the features mentioned here came after.

Database Editor — Component breakdown
  • Pagination over full-key loading — DataStore key spaces can be enormous. The query engine loads in pages to avoid hitting API rate limits and keep the UI responsive.
  • Value diffing before writes — the plugin compares the edited value to the original before calling SetAsync, preventing unnecessary writes that would consume quota.
  • Read-only mode by default — developers must explicitly enable write mode to prevent accidental data corruption on live games.

Game Optimiser Plugin

Profiling and performance analysis for Roblox — surface the real cost of textures, scripts, and memory.

Roblox has a built-in profiler, but most developers won't know how to read it or what to do with what it shows. This plugin takes that information and translates it into something actually actionable — here's what's expensive, here's why, here's where it is. It's not trying to replace the profiler, just make it approachable for developers who would otherwise ignore it entirely.

Optimiser — Analysis pipeline
  • Separate analyser modules per asset type — texture, script, and instance analysis have different logic and data sources. Keeping them separate makes each easier to extend without breaking others.
  • Sort output by cost, not by name — the most expensive asset always appears first so developers immediately know where to focus.
  • Click-to-select in report — clicking a flagged asset selects it in the Studio viewport, so fixing it requires no manual searching.

YOLO Alone

Solo survival horror — build atmosphere through sound, lighting, and scripted AI events.

A single-player horror game set in a forest. The tension comes from scripted environmental events — flickering lights, audio cues, triggered entity movement — rather than constant action, making atmosphere the core mechanic.

YOLO Alone — Atmosphere engine
  • Atmosphere-first design — horror from suggestion, not constant threats. The event scheduler fires audio and lighting cues on a randomized timer so no two playthroughs feel identical.
  • Spatial audio as primary feedback — the player hears something before they see it, creating dread without requiring complex 3D models.
  • Entity pathfinding over scripted paths — using PathfindingService keeps enemy movement feeling organic rather than mechanical.

Webhook System

Roblox → Discord event pipeline with structured payloads, rate limiting, and embed formatting.

Honestly, this was a learning project. I wanted to understand how HTTP requests actually worked and this was how I figured it out — building something real rather than following a tutorial. It ended up being a solid reusable module, but the real value was what it taught me about request flow, rate limiting, and working with external APIs. Everything that came after this was built on that foundation.

Webhook System — Delivery pipeline
  • Queue + rate limiter before HttpService — Discord enforces a 30 requests/minute limit per webhook. The queue batches rapid events so no requests get dropped.
  • Separate payload formatter module — embed structure is defined once in the formatter, not scattered across every script that fires events. Changing the embed layout requires editing one file.
  • Retry logic with backoff — transient network failures shouldn't silently drop events. Failed requests are re-queued with exponential backoff.

Background

I'm a self-taught Roblox developer who started out building games and progressively shifted toward systems engineering — the architecture, tooling, and plugin infrastructure that other developers build on top of. Over 4+ years I've shipped plugins used by real developers, cross-platform integrations connecting Roblox to the web, and reusable frameworks designed to be commercially viable.

On the web side, my focus is front-end — the UI, the layout, the interaction layer. I'm not a back-end developer, and I don't claim to be. What I build well is the part users actually see and interact with, whether that's a Studio plugin panel or a browser-based dashboard that talks to Roblox data.

I run KDR Studio, a commission-based development business, taking on custom Roblox systems work and recruiting specialist collaborators for larger projects.

Why mostly plugins?

Game systems can be made by almost anyone — and increasingly by AI too. Tools like Lemonade AI can already generate functional, specific game systems. Plugins are a different story. The hard part isn't the code itself, it's the decisions you make before you write any of it. How will the system work? What does the architecture look like? Because if you get that wrong and keep building on top of it, you can't just patch it — you have to scrap it and start over. Every structural mistake compounds. That forces you to think carefully and get things right before you commit, which is a skill that takes real experience to develop. AI can't replicate that judgment yet, and that's exactly what makes plugin development worth doing.
